# Hospital LiFi Handoff System

A Flask web application that models secure file and message transfers between hospital roles over simulated LiFi optical zones. It combines role based dashboards, encrypted file storage, handoff approval and audit logs, zone management, and a synthetic comparison of DSDV and GPSR routing metrics.

> **Project scope:** This repository is a software prototype. It does not connect to LiFi transmitters, wireless sensor hardware, or a real hospital network. The routing metrics are generated by a Python simulation.

## Features

- Signup, login, account approval, and dashboards for administrators, asset managers, and hospital users.
- File uploads encrypted with Fernet and stored under `uploads/encrypted/`; supported extensions and the 50 MB limit are configured in `config.py`.
- Role based file sharing, download and decryption flows, integrity hashes, and handoff activity logs.
- Encrypted messages exchanged between roles.
- Optical zone activation requests and administrator approval.
- A dashboard/API comparison of simulated DSDV and GPSR latency, throughput, packet delivery ratio, and energy use.
- APScheduler jobs for handoff cleanup, file integrity checks, and statistics logging.
- TinyDB JSON storage in `data/hospital.json` (local runtime data; not included in Git).

## Roles

| Role | Main capabilities |
| --- | --- |
| Administrator | Approve accounts and zones, review files and handoff logs, manage shared-secret access, and view routing metrics. |
| Asset manager | Receive shared files, upload reports, validate handoffs, exchange messages, and request optical zone changes. |
| Hospital user | Upload files, access own/shared files, and exchange confidential messages. |

New non-administrator accounts require administrator approval before accessing role dashboards. The signup page offers the user and asset-manager roles. The source does not provide default administrator credentials or an administrator bootstrap command.

## Requirements

- Python 3.10 or newer is recommended.
- Runtime packages: Flask, TinyDB, `cryptography`, APScheduler, Celery, and pytz.

The complete Python dependency list is in `requirements.txt`, including Flask, TinyDB, `cryptography`, and `python-dotenv`.

## Setup and run

From the project root, create and activate a virtual environment, then install dependencies:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

On Windows, activate the environment with `.venv\Scripts\activate` instead of the `source` command.

Create a local `.env` file from the example, then replace the placeholder values with generated keys:

```bash
cp .env.example .env
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
python -c "import secrets; print(secrets.token_hex(32))"
```

Put the first generated value in `FERNET_KEY` and the second in `SECRET_KEY`. Keep `.env` private; it is excluded from Git. `FLASK_DEBUG` defaults to `false`.

Start the Flask development server:

```bash
python app.py
```

Then open <http://127.0.0.1:5000>. The application creates its working directories on startup. `init_zones.py` can populate and activate the default optical zones when the database has none.


## Data and configuration

- `data/hospital.json` is the active local database. It is ignored by Git because account and file metadata may be sensitive. Back it up before experimenting or replacing it.
- New encrypted uploads are written to `uploads/encrypted/`. Some existing file records may point to paths from the machine where the sample data was created, so those historical files may not be available on another system.
- Upload size, allowed extensions, database location, and other settings are defined in `config.py`.
- The app starts APScheduler as part of application import/startup. Celery tasks are defined with a filesystem broker, but a Celery worker is not needed for the normal Flask startup flow.

## Security limitations

This configuration is for demonstration only. The Fernet key and Flask secret key are loaded from environment variables (or a local `.env` file), and `.env` must never be committed. The sample `.env.example` contains placeholders only. Do not use this prototype with real patient information or expose it to an untrusted network. Before deployment, use securely managed secrets, keep debug mode disabled, review account provisioning and access controls, and protect the database and upload directories.

## Useful routes

- `/signup` and `/login` — account creation and login
- `/admin/dashboard` — administrator overview
- `/asset-manager/dashboard` — asset-manager overview
- `/user/dashboard` — hospital-user overview
- `/api/statistics` — authenticated system statistics
- `/api/active-sessions` — authenticated handoff activity
- `/api/routing-comparison` — authenticated synthetic DSDV/GPSR comparison

Most dashboard and API routes require an authenticated, approved account with the appropriate role.
